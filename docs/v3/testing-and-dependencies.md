## Existing verification and dependency management

The repository has no application test suite, root `package.json`, root `composer.json`, or application dependency lockfile. The only workflow, `.github/workflows/lint.yaml:1`, installs the runner's default PHP CLI and runs `php -l` over PHP files. This detects syntax errors, but cannot verify authentication, authorization, forms, API behavior, charts, database compatibility, upgrades, or responsive layout. A dependency's own configuration such as `libraries/include/RandomCompat/composer.json` is not an application test harness.

The audited legacy runtime is Apache/PHP/MySQL with Git installation and self-update: `README.md:15`, `install.php:75`, `libraries/vcs.php:58`. Browser libraries are committed under `webroot/`; PHP libraries are copied into `libraries/`. Record exact source provenance and licenses before replacing copied code. Do not infer an upstream release version from copyright years or file dates.

## Extension compatibility is a migration gate

Parameter controls and plots are plugins, not just fixed forms:

* Default controls are scanned from `libraries/elements/` (`core/util.php:234`), then per-system controls are added from `webroot/systems/<id>/parameters` (`core/system.php:79`). An element has a config, arbitrary build/render HTML, an optional PHP processor, and optional copy logic (`core/element.php:47`, `core/element.php:77`, `core/element.php:110`).
* Plots likewise declare required assets and provide PHP processing plus HTML/JavaScript rendering (`core/plot.php:72`, `core/plot.php:79`). Results combine overall plots and grouped per-job plots (`libraries/results.php:245`).
* `System::getResultPlots($plots)` currently receives its array by value (`core/system.php:90`), so appended custom plots do not reach the caller. This is a code-level defect to characterize, not a reason to remove the intended extension capability. Custom type collisions also need a defined policy; existing loops do not consistently express override precedence.

The authorized read-only deployed-file inventory found usage of every bundled parameter control and plot type, plus legacy result-configuration formats. No custom `parameters/` or `results/` directories, root PHP system pages, or `system_assets` directories were observed in the inspected installation. These findings define representative fixture coverage without reducing general extension support. The proposed compatibility design retains server-side processors with explicit versioned data schemas and an Angular renderer registry; define and test the extension contract for other installations before final removal. Arbitrary old HTML/inline script fragments cannot be assumed to run safely or correctly as Angular components. A temporary compatibility adapter must be an explicit transitional decision, with a removal test and no hidden dependency on Bootstrap 3/jQuery in the final UI.

## Test data and isolation

Create disposable test installations for both the pinned legacy commit and the v3 branch using Apache with mod_rewrite, PHP 8.3, and MySQL 8.0. Include selected supported newer PHP versions in the compatibility matrix. Use separate databases, temporary filesystem roots and local fixture VCS repositories. Never point tests at an existing installation, production database, configured CEM/MAAS host, network mount, or real evaluation agent. All services with side effects need local fakes or controlled disposable services.

Seed deterministic synthetic data from a fixture builder rather than reusing `libraries/demo/demo.sql`, whose historical, large result records are hard to review and do not cover the required permission and boundary cases. The fixture builder should use stable identifiers while allowing separate old/new database IDs; compare semantic records after ID mapping. Use explicit-offset instants for new API cases and legacy naive local wall times for historical cases. `Europe/Zurich` is authoritative for application/display interpretation. Inspect legacy serialization and column behavior, preserve the meaning of stored naive datetimes, and never relabel them as UTC merely because a dump includes a UTC session directive. Include ambiguous and nonexistent DST wall times without guessing an offset or rewriting historical values.

Source evidence for the time distinction is `webroot/index.php:56`, which sets PHP's local timezone to `Europe/Berlin`, and `chronos.sql:5`, which sets the dump session timezone without adding offsets to naive `DATETIME` values. Combined with the authorized read-only metadata inspection, the migration preserves historical local wall times under the authoritative `Europe/Zurich` policy. New explicit-offset contracts must not retroactively invent offsets for ambiguous legacy records.

## Executable test roadmap

The following paths/commands are proposed contracts to create in the testing implementation slice; they do not exist yet. Each feature in the separate UI inventory should map to one or more stable test IDs, permission cases, fixture, layer, expected result, and final evidence. Use an explicit `pending` state until implemented; a written test case is not a passing test.

1. Add `tests/fixtures/`, a deterministic fixture command, disposable Apache/PHP/MySQL orchestration, and a test configuration with environment-only secrets. Publish a single `scripts/test-stack` entry point that starts isolated services and cleans them on success or failure.
2. Add PHP domain characterization tests using a PHPUnit release compatible with PHP 8.3, test helpers for Element/Plot processors, and a database integration suite. Proposed commands: `composer test:unit` and `composer test:integration`.
3. Add API tests against the real disposable HTTP server for authentication, permissions, validation, mutation and binary response contracts. Proposed command: `composer test:api`. A versioned API schema should be checked and used by frontend contract tests; raw HTTP assertions remain necessary for cookies, status codes and downloads.
4. Add Playwright browser tests with separate legacy/v3 base URLs and common scenario semantics. Proposed commands: `npm run test:e2e:legacy`, `npm run test:e2e:v3`, and `npm run test:parity`. Route/locator adapters may differ while expected business results remain shared. Avoid snapshots of entire volatile pages as a proxy for function coverage.
5. Add Angular component tests for interactive controls and loading/error states, type-check/lint/build commands, and accessibility checks. Proposed commands: `npm run test:components`, `npm run typecheck`, `npm run lint`, and `npm run build`.
6. Add a release smoke suite that installs the built artifact from scratch and upgrades a legacy fixture installation without Node/Composer. Proposed command: `scripts/test-release`. The suite also verifies back/forward/deep links, every local asset, UI version updates and agent compatibility.

## Legacy/new comparison and defect policy

Run the pinned legacy build and v3 from the same synthetic starting state, with equal roles and inputs. Build a parity ledger linking each inventory feature to test IDs and evidence. For reads, compare normalized records, visible meaning, counts, enabled actions and result datasets. For writes, compare database rows, files, events, generated jobs and authorization outcomes. Ignore implementation details such as CSS classes, framework DOM structure, generated IDs, ZIP compression or random ordering where these have no product meaning.

Use screenshots to review layout and intended design changes, not to demand pixel equality with the old UI. Check actual numeric chart data and independently calculated expected results; matching two identical wrong implementations is not correctness. Add approved improvements as explicit new expectations in the ledger.

Record existing failures as baseline defects with a minimal reproducer and proposed corrected behavior. Examples found by static inspection include the custom plot by-value issue, global DOM IDs and `const copy` in multiple software-version controls (`libraries/elements/software-version-list/render.template.html:10`), debug `var_dump` output (`controllers/builder.php:103`), negative interval steps that can fail to terminate, and multi-parameter plot loops that may double-count a metric. These are test targets, not claims of runtime reproduction. Do not freeze unsafe behavior, infinite loops or incorrect statistics as mandatory v3 behavior.

Removal gate: every available legacy feature is mapped, all approved functional expectations pass, defects are resolved or explicitly agreed, browser/API/domain tests pass, install/upgrade/agent smoke tests pass, and the parity ledger has no unexplained omissions. Only then delete legacy routes, PHP UI views/templates, old assets and obsolete dependencies. Preserve historical data/configuration import capability where required.

## Build, release and self-update without production Node

The confirmed distribution is CI-built installable packages. Normal source pull requests contain frontend source and lockfiles, not generated production bundles. The existing installer clones a selected branch (`install.php:107`) and the self-updater checks out and pulls that branch (`libraries/vcs.php:78`); both must migrate to package consumption while preserving branch selection. Production runs Apache/PHP and the built Angular UI without Node.js or Composer.

Selected release contract:

1. Pin Node/build tools, Angular/AdminLTE/frontend dependencies and PHP dependencies in the source tree. CI performs clean locked installs, tests and a production build; include free third-party licenses and dependency provenance in the package. Keep generated bundles out of source PRs.
2. Publish an immutable, checksummed package containing PHP code, production PHP dependencies if used, compiled Angular HTML/CSS/JS/fonts/icons/logo, API contract/version metadata and installation/upgrade instructions. Record source commit, selected source branch, build ID and runtime requirements. Exclude node_modules, caches, development secrets, uploaded data, logs, test traces and local IDE files.
3. Provide branch-to-package metadata through a defined release-provider contract. The installer and superadmin self-updater retain branch selection, resolve the available compatible package for that branch, verify integrity and source/build metadata, and present actionable failures when the package is unavailable or incompatible. They must not fall back to serving unbuilt source or running npm/Composer in production. Test this with a fake provider and real disposable package installation.
4. Download and extract into a staging directory, verify the complete package and PHP 8.3/runtime requirements, apply versioned database migrations with an explicit backup/rollback policy, then switch the served release coherently. Keep `config.php`, system repositories, uploaded data, logs and runtime state outside replacement paths or explicitly preserve them. Test failed download, integrity mismatch, incomplete extraction, failed preflight/migration and interruption without leaving mixed backend/frontend releases.
5. Keep the prior verified package and release metadata for rollback. Roll back PHP/backend/assets together and define database compatibility before enabling rollback for a migration; a binary package rollback must not silently reverse or lose user data. Test successful upgrade/rollback, unavailable prior package and a failure during activation. A source Git checkout is not a substitute for a tested package rollback.
6. Include a build identifier known to both the loaded UI and an appropriately public lightweight version endpoint. Return `Cache-Control: no-store` for version metadata and the entry document; use content hashes and long immutable caching for bundle assets. Retain compatible prior hashed chunks long enough for existing tabs until update/reload. Omit a service worker unless a clear requirement justifies its additional tested cache/update strategy.
7. Angular checks version metadata at a modest interval and when returning to the tab, pauses unnecessary work in background, handles failures quietly and offers the bottom-centered reload action. No forced refresh. Preserve or warn about unsaved changes when the user chooses reload. A rolled-back deployment must also be detectable as a different active build without assuming build IDs are numerically increasing.
8. CI proves a clean installation and a legacy-to-v3 upgrade using the delivered package on Apache/PHP 8.3/MySQL 8.0 with Node/npm/Composer absent. Verify preserved system config files, both legacy/current result formats, historical date semantics, remembered sessions where intended, data, downloads, CEM/agent protocol compatibility, branch/package selection and rollback with a prior frontend/API pair. Run the same package checks on selected supported newer PHP versions.

Dependency updates should be separate reviewable slices where possible: test/fixture baseline; PHP compatibility/packages; locked frontend build/AdminLTE; API and feature migrations; parity fixes; release/update support; legacy cleanup. Automated security/license checks and scheduled update PRs can follow once reproducible manifests exist. Avoid treating a bulk file replacement as proof that every dependency is current or compatible.

## CI acceptance stages

Every PR should run PHP lint on PHP 8.3 and the selected supported newer versions, domain/integration/API tests, Angular locked install/type/lint/component tests/build, and the browser scenarios relevant to the change. Run the full parity suite before removal, plus release/install/upgrade checks on release candidates. Preserve failure-only screenshots, traces, relevant logs, schema diffs and test results as CI artifacts; never commit them to the repository. Label destructive infrastructure scenarios separately and execute them only against disposable fakes.

The planning PR may contain this roadmap without executable tests. Later PRs must report what actually ran, the exact versions tested, feature IDs covered and remaining gaps. “Everything works” is not a verifiable acceptance record.
